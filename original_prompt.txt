### 1.2 Bug inventory (full list, not just the top 3)

**Correctness bugs (cause wrong predictions):**
1. Confidence voting uses raw sequence accession IDs instead of taxonomic labels (§0, bug 1).
2. Non‑deterministic hash‑based tokenization (§0, bug 2) — breaks reproducibility *and* correctness simultaneously, and will silently re‑break every time the HF Space restarts, even after a partial fix, unless `PYTHONHASHSEED` is pinned or `hash()` is removed entirely.
3. `kmerize()` returns a Python `set`, so `list(kmerize(...))[:MAX_SEQ_LEN]` both (a) loses sequence order — the CNN's positional convolution gets a shuffled bag of k‑mers, not the sequence — and (b) truncates to 500 k‑mers in **hash‑bucket order, not sequence order**, so for any query longer than ~500 unique 6‑mers, *which* k‑mers survive truncation is arbitrary and changes every restart.
4. Reference novelty stats (`mean=0.9, std=0.05`) appear to be an un‑calibrated placeholder (§0, bug 3).
5. `jaccard(a, b) = |a ∩ b| / |a|` is **not** the Jaccard index (that's `|a∩b|/|a∪b|`) — it's a query‑containment coefficient. Not necessarily wrong to use, but mislabeled, and worth re‑validating the 0.95 threshold against the correct semantics.
6. Deterministic matching only ever checks the **family**‑level `subsampled.fasta` cache — there's no equivalent fast‑path at genus level, and no kingdom‑level fast rejection, so every non‑near‑duplicate sequence pays the full ML cost even when it's obviously the wrong kingdom (e.g., a plant sequence sent with `marker=16S`).
7. `encode_sequence` uses **k=6** for the CNN tokenizer while the deterministic matcher uses **k=21** — not itself a bug, but if the embedding model was actually trained expecting a different k or a different vocabulary scheme than what's in this code, that's an unknown mismatch (see 1.3).

**Design/engineering weaknesses (not wrong, but fragile or wasteful):**
8. `HASH_DIM=100_000` hash buckets for what is, at k=6, only **4,096** possible distinct DNA k‑mers (4⁶). You're paying for a lossy, seed‑dependent hash into a 100k‑slot table to represent something that has an exact, collision‑free, 4,096‑entry encoding available. This is strictly worse than the alternative on every axis (correctness, size, speed, reproducibility).
9. No training script is present anywhere in what you gave me — only inference/serving code. We need to confirm whether one exists elsewhere before deciding "fix" vs. "rebuild."
10. No real MLOps scaffolding exists in the deployed code despite the report claiming DVC/W&B/Cron/Docker smoke tests — this is a gap between the report and reality worth closing for real, since it's literally the deliverable of the MLOps course component.
11. `log_history` writes to a flat `analysis_history.jsonl` on local disk — on Hugging Face Spaces this is ephemeral and will vanish on every container restart/rebuild. Fine for a demo, not fine as an audit trail or as a source of retraining data.
12. `HTTPException` messages leak the internal `VALID_MARKERS` set structure and no input validation exists on sequence content (no length cap enforcement pre‑kmerization, no ambiguous‑base handling beyond `"N" not in kmer`).

## PHASE 2 — Fix / Repair / Redo

### 2.1 Non‑negotiable fixes (needed under *any* architecture choice)

These are correct regardless of which option you pick in 2.2–2.4:

1. **Kill `hash()` for tokenization.** Replace with an exact k‑mer vocabulary. For k=6 that's a fixed 4,096‑entry lookup table computed as a base‑4 encoding (A=0,C=1,G=2,T=3 → integer), no hashing, no collisions, no seed dependency, deterministic forever. If you later want larger k, use a seeded, fixed, non-cryptographic hash (e.g. `hashlib.blake2b(kmer.encode(), digest_size=4)` or `mmh3.hash(kmer, seed=42)`) — never Python's built‑in `hash()` on strings.
2. **Preserve sequence order** when building the token sequence for the CNN — iterate a sliding window left‑to‑right, don't dedupe into a `set`. If you want deduped *and* ordered, use `dict.fromkeys()` instead of `set()`.
3. **Fix the confidence/voting logic** to aggregate taxonomic labels (family name at the family index, genus name at the genus index), not accession IDs. This requires the index's `ids.npy` (or a side‑car mapping) to carry the right label per rank.
4. **Recompute novelty statistics empirically** — run the trained model over a held‑out reference set per marker/rank, record the real mean/std of nearest‑neighbor distances, and bake *that* into `meta.json`, not a placeholder.
5. **Any of the above requires retraining regardless.** Even if you only fix the tokenization bug, the current checkpoint's embedding weights are tied to whatever (probably lost) hash‑seed produced them during training — there is no way to "recover" them by patching only the inference code. Budget for a full retrain, not a hot patch.

### 2.2 [DECISION] Embedding backbone

| Option | What it is | Pros | Cons |
|---|---|---|---|
| **A — Minimal repair** | Keep the current CNN(embed→conv→maxpool→fc) shape, just fix tokenization (2.1) and retrain | Fastest to ship, cheapest compute, matches "CPU‑only, sub‑50ms" claim in the paper draft | Ceiling on accuracy; still a from‑scratch model with only your reference data to learn from |
| **B — Exact k‑mer vocab + slightly deeper CNN** | Same family of model, but proper embedding table (2.1.1) + batch norm + maybe a second conv block, as literally described in the paper draft's architecture bullet list | Still CPU‑friendly, closer to what's already written up, easy to defend in the paper as "we implemented what we said we would" | Still capped by training‑data volume/diversity for contrastive learning |
| **C — Pretrained genomic foundation model backbone** (e.g. DNABERT‑2, HyenaDNA, Nucleotide Transformer), fine‑tuned or used as a frozen feature extractor, with a small projection head trained on your data | Highest likely accuracy ceiling; you also get a paper baseline "for free" (DNABERT is already on your required baseline list) | Breaks the "CPU‑only, sub‑50ms" story from the original paper — needs GPU for reasonable latency at scale; heavier deployment; slower iteration |

**My recommendation:** **B**, with C run separately as one of the required baseline comparisons in Phase 4 rather than as the production backbone. That keeps HTRP's actual selling point (cheap, fast, CPU‑only, explainable) intact while still giving you the DNABERT/foundation‑model number the paper checklist asks for.

### 2.3 [DECISION] Training objective

The two source documents disagree (triplet+genus-supervised vs. unsupervised instance‑contrastive), and you separately asked to "replace the current contrastive loss with InfoNCE or SupCon" — which presupposes a contrastive loss already exists to replace. Since there's no training script to inspect, I'd resolve this by building straight from your Phase 4 requirement instead of guessing at history:

| Option | Description | Notes |
|---|---|---|
| **A — Supervised Contrastive (SupCon)** | Use genus (or family) labels as the positive/negative signal within a contrastive framework | Satisfies "sequences from the same genus cluster together" (paper draft) **and** "contrastive learning" (your ablation checklist) in one implementation. This is what I'd default to. |
| **B — InfoNCE, self‑supervised (augmentation-based)** | No taxonomic labels used; positives = two augmented views of the same sequence (e.g. random k-mer dropout, reverse-complement, subsequence crop) | Matches the MLOps report's "unsupervised, instance‑level" description; better for genuinely open‑set/undersampled taxa where labels are sparse or unreliable |
| **C — Train both** | Build the harness so either loss is swappable via a flag | Directly produces the "Replace Contrastive Loss" ablation number your paper checklist needs (item 4) instead of you having to guess what "the current loss" was |

**My recommendation: C.** It's barely more work than A alone if you build the training loop with a pluggable loss from day one, and it directly produces a checklist item you need anyway.

### 2.4 [NEW CAPABILITY] Adaptive marker detection

Right now the API requires the caller to already know the marker gene (16S/18S/CO1/etc.). You want: raw sequence in → marker inferred automatically. This isn't in either source document — it's new scope.

**Why this is tractable:** different marker genes have very different k‑mer composition and length distributions (16S rRNA vs. COI protein-coding vs. ITS spacer regions look nothing alike statistically). This is a much easier classification problem than family/genus assignment.

| Option | Approach | Cost |
|---|---|---|
| **A — Cheap classical classifier** | k‑mer frequency vector (e.g. k=4, 256‑dim, trivially fast) → logistic regression or small SVM over your 7 marker classes | Minutes to train, ~microseconds to run, easy to explain in the paper as a legitimate "kingdom/marker routing" stage consistent with the original paper's k=6 sketch idea |
| **B — Small CNN, same architecture as the embedder** | Reuse the k‑mer tokenizer + a lightweight CNN head trained to predict marker class instead of embedding | More consistent engineering (one tokenizer, two heads), marginally more accurate, marginally more expensive |

**My recommendation: A first** (build it in an afternoon, it'll likely hit >95% accuracy since marker discrimination is an easy problem), fall back to B only if A's accuracy disappoints on real mixed/ambiguous samples. Either way this becomes **Stage 0** of the pipeline, run before anything marker‑specific.

### 2.5 [NEW CAPABILITY] Corrupted vs. genuinely novel

Also new scope — neither document addresses this, and it's central to what you said you actually want the system to do.

Proposed approach — two complementary layers:

1. **Cheap deterministic QC gate (before any ML):** ambiguous‑base fraction, homopolymer run length, length bounds for the detected marker, GC content sanity range, k‑mer Shannon entropy (very low entropy ⇒ repetitive/artifact, not biology). This catches obvious garbage for free, before spending FAISS/embedding compute on it.
2. **Learned corruption classifier:** train on real reference sequences vs. synthetically corrupted ones you generate yourself (random shuffles, random substitutions at high rate, truncated fragments, chimeric splices of two different references, homopolymer insertion). Output a `p(corrupted)` distinct from `p(novel)`.

The key output‑design change this implies: **`prediction` becomes three‑way, not two‑way** — `KNOWN`, `NOVEL`, `CORRUPTED` — each with its own probability, rather than forcing corrupted input to be mislabeled as either.

### 2.6 Output/API redesign

To match what you described wanting ("random sequence in → matched organism, or top‑10 similar organisms, plus novelty/corruption probability"), the response shape needs to change from today's per‑rank KNOWN/NOVEL boolean into something like:

```json
{
  "detected_marker": {"label": "16S", "confidence": 0.97},
  "quality": {"corrupted_probability": 0.02, "flags": []},
  "novelty": {"novel_probability": 0.81, "z_score": 2.9},
  "top_matches": [
    {"organism": "Vibrio harveyi", "rank_matched": "genus", "similarity": 0.88, "accession": "KX118041.1"},
    ...
  ],
  "path": "deterministic | embedding | novel",
  "explainability": { ... as today, kept and extended ... }
}
```
This is a Phase 2 deliverable (schema + backend change), not just a Phase 6 writing exercise — flagging it here so it's scheduled with engineering time, not left implicit.

## PHASE 3 — Testing, Reliability, Consistency

1. **Determinism test (the one that would have caught bug #2):** run the identical query 20 times across fresh process restarts; assert identical output. Add this to CI.
2. **Regression fixtures:** a small hand‑picked set of sequences per marker with known expected family/genus, committed to the repo; must stay `KNOWN` and correct after every retrain or deploy.
3. **Synthetic adversarial set:** random DNA, reversed sequences, all‑N, homopolymer runs, truncated fragments — assert these land in `CORRUPTED` or `NOVEL` as appropriate, not silently in `KNOWN`.
4. **Held‑out known‑taxa set:** sequences excluded from training but from taxa the model *has* seen elsewhere in the same family/genus — assert accuracy stays in a defined band; this is your canary for "silent accuracy degradation," a risk your own MLOps report already names.
5. **Load/latency test:** batch of e.g. 10,000 sequences through `/infer_batch`, confirm the paper's sub‑50ms/sequence target (or your revised target if Option C in 2.2 is chosen) actually holds, on the actual deployment hardware, not just locally.
6. **API contract tests:** frontend/backend schema agreement (this becomes more important once 2.6's response shape changes — the frontend JS will need matching updates).

Exit criterion for Phase 3: the same query, run repeatedly and across restarts, gives the same answer, and that answer is *correct* on the regression fixtures. Don't start Phase 4 measurement work until this holds — otherwise your baseline numbers will be measuring noise.
